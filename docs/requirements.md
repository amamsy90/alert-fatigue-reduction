# Requirements and traceability

**System:** AI-Assisted On-Call Queue (`app/`)
**Version:** 1.0.5 · **Status:** baselined after the Phase 0 review fixes

This document states what the system must do (functional requirements, FR), how well it must do it (non-functional requirements, NFR), who it is for (user stories with acceptance criteria), and where each requirement is verified (traceability matrix). Test names refer to functions in `app/tests/`; "results" refers to files in `app/results/` checked by `run_validate.py`.

---

## 1. Stakeholders

| Stakeholder | Goal | Main touch points |
|---|---|---|
| **On-call engineer** | See at most K items a day, in the order a live system learns about them, and not miss the real faults | Queue page, pager channel, Real / Noise marks |
| **Team lead / SRE** (operator) | Install it safely next to a real pager, decide when it may page, keep secrets safe | Docker, Connectors page, env vars, Live switch |
| **Evaluating team** | Find out on their own data, before trusting it, whether it beats the rules they run | Evaluate my data page, CLI `evaluate` / `tune` |
| **Course examiner / researcher** | Reproduce every published number | Experiment scripts, `run_validate.py`, CI |

## 2. Functional requirements

| ID | Requirement | Priority |
|---|---|---|
| **FR-1** | The system shall accept alerts from an Alertmanager webhook (v4) or a JSON `{alerts: [...]}` list, keep only firing alerts, and buffer them until a scoring job runs. | Must |
| **FR-2** | The system shall not buffer an alert whose content was already received within `INGEST_DEDUP_HOURS` (default 24). | Must |
| **FR-3** | The system shall accept a CSV batch upload of alerts, metrics and past faults. | Must |
| **FR-4** | The system shall pull memory series from a configured Prometheus server. | Should |
| **FR-5** | The system shall detect a metric jump (a rise above the median of the previous window: absolute, relative or robust mode) and confirm it at its N-th hot point. | Must |
| **FR-6** | The system shall detect slow leaks with a long-window rule and drop a leak already covered by a shown fast jump. | Should |
| **FR-7** | The system shall report a monitoring gap `gap_minutes` after a series' last point, including a feed that is still silent now. | Must |
| **FR-8** | The system shall score log alerts with a cost-sensitive classifier (a miss costs 10× a false alarm) when labels or marks exist, and fall back to severity rules when they do not. | Must |
| **FR-9** | The system shall build a daily queue of at most K items, first come first served, with log alerts capped at `alert_share` of K; an alert on a service whose shown jump is still open rides on it without a slot. | Must |
| **FR-10** | The system shall let a user mark any shown item Real or Noise, use the marks as labels in later runs, and remind the user to retrain after 7 days or new Real marks. | Should |
| **FR-11** | The system shall run in shadow mode by default and record what Live mode would have paged. | Must |
| **FR-12** | In Live mode the system shall page PagerDuty, Slack and Opsgenie with the same item list, only from webhook-ingest jobs, and only for items shown since the last job (per channel). | Must |
| **FR-13** | The system shall evaluate any metric table (with optional events and past problems): tune on the early part of each series, score the rest once against a static rule, a rate rule and the jump rule with a chance line, and let the user apply the best setting to the live queue. | Must |
| **FR-14** | The system shall offer the same scoring and evaluation from a command line (`score`, `evaluate`, `tune`). | Should |
| **FR-15** | The Connectors page shall show which channels, keys and URLs are configured without ever returning a secret in full. | Must |
| **FR-16** | Every published result shall be regenerated by a script, and `run_validate.py` shall fail when a number in `FINAL_REPORT.md` no longer matches the result files. | Must |
| **FR-17** | Every trained model shall be kept as a version with a model card; a new version shall become active only if its held-out cost is no higher than the active model's on the same alerts; an operator shall be able to roll back to any kept version. | Must |
| **FR-18** | The system shall expose service, job, paging, model and data health as Prometheus metrics (`/metrics`) and as a checked summary (`/monitoring`). | Must |
| **FR-19** | Every experiment run shall be logged with its code version, configuration, data fingerprint, outputs and metrics. | Should |
| **FR-20** | Webhook rows without a usable timestamp or source shall be rejected with a reason and never block later jobs. | Must |
| **FR-21** | GPU training shall be optional. The default install and CI shall run without the `gpu` dependency group. Every GPU path shall fall back to the scikit-learn classifier when CUDA or the GPU library is missing, and the saved model shall remain a skops archive that loads on CPU. | Must |
| **FR-22** | An LLM shall not change which items are queued or paged unless `LLM_TEMPLATE_FEATURES` is on. Live paging rules are unchanged. The flag is off. A time-split ablation on the synthetic alert sample did not show a gain, and the GAIA full-queue run was not available, so the flag stays off. Shadow notes do not select items. | Must |
| **FR-23** | An LLM prompt shall contain only fields known at decision time. Realised fault labels and later rows shall not be included. Shadow notes use that prompt. The classifier already excludes the realised label from its inputs. | Must |

## 3. Non-functional requirements

| ID | Quality | Requirement | Measure |
|---|---|---|---|
| **NFR-1** | Causality | No queue decision may use data from later than the moment it is made. | Adding later data never changes an earlier decision (tests) |
| **NFR-2** | Security | Access needs a password except from this machine or a private network without a proxy; Prometheus targets are checked against SSRF; cross-site state changes and DNS rebinding are refused; the ingest token is header-only; secrets are never returned or logged; request bodies are capped while streaming. | Security tests; threat model (`docs/threat_model.md`) |
| **NFR-3** | Safety | Nothing is paged unless Live mode is on, a channel is configured, a login password is set, and the job is a webhook-ingest job. | Safety tests |
| **NFR-4** | Reliability | One scoring job and one evaluation at a time (409 otherwise); no lost settings writes; database connections closed, WAL on; alerts stay buffered when scoring fails; a retry never pages the same item twice on a channel that already delivered it. | Reliability tests |
| **NFR-5** | Performance | Median time from fault start to the confirming point ≤ 1 minute at 30 s sampling; `/health` answers without calling Prometheus; the full GAIA pipeline runs on a laptop in under an hour. | `stats.confirm_minutes_median` = 0.72 min; health test |
| **NFR-6** | Auditability | Every decision stores a reason; every change to Live mode, keys, the Prometheus URL or settings is logged with user and outcome. | Queue rows; audit test |
| **NFR-7** | Maintainability | CI gates every change: lint clean, no mypy errors (budget 0), line coverage ≥ 85%. | `.github/workflows/ci.yml` |
| **NFR-8** | Portability | Runs on Python 3.10–3.12 and as a Docker image built from hash-pinned dependencies. | CI matrix and Docker job |
| **NFR-9** | Data retention | Old jobs and evaluations are pruned (`JOB_RETENTION`, `EVAL_RETENTION`); Real / Noise marks are kept. | Retention tests |
| **NFR-11** | Performance under load | With 50 concurrent users: p95 latency ≤ 1 s, ≥ 20 requests/s, ≤ 1% errors. | `perf/load_test.py`: 0.32 s, 228 req/s, 0% |
| **NFR-10** | Effectiveness | On GAIA at K = 20 the jump detector beats a Prometheus rate rule in every walk-forward week, with fewer false items a day. | `walkforward.jumps_tuned.wins` = 8; results |

## 4. User stories and acceptance criteria

**US-1 — See only what matters today** (FR-5, FR-7, FR-9, NFR-1)
*As an on-call engineer, I want at most K items a day in the order they happen, so that my attention goes to real faults.*
- Given a day with more candidate items than K, when the queue is built, then exactly K items take slots and each was chosen without looking at anything later that day.
- Given an alert on a service whose shown jump is still open, then the alert appears inside the jump and uses no slot.
- Given a series that stops sending data, then a gap item appears `gap_minutes` after its last point, even if no series has sent data since.

**US-2 — Plug in my alerts** (FR-1, FR-2, NFR-4)
*As an operator, I want to point Alertmanager at the app, so that alerts arrive without code.*
- Given an Alertmanager v4 payload, when it is posted to `/ingest/alertmanager`, then firing alerts are buffered and resolved ones ignored.
- Given the same alert is posted twice (a retry), then it is buffered once and the response counts one duplicate.
- Given scoring fails, then the buffered alerts stay for the next run.

**US-3 — Try it without risk** (FR-11, NFR-3)
*As a team lead, I want the tool to run beside our pager without paging anyone, so that we can judge it first.*
- Given a fresh install, then shadow mode is on and every job records what Live would have paged.
- Given sample, GAIA or Evaluate runs, then nothing is paged even if Live is on.

**US-4 — Turn paging on deliberately** (FR-12, NFR-2, NFR-3, NFR-6)
*As a team lead, I want Live paging to need several deliberate steps, so that no one turns it on by accident or from outside.*
- Given no `APP_PASSWORD`, when someone asks for Live, then the request is refused and the refusal is logged.
- Given a password and a channel, when `LIVE` is typed exactly, then Live turns on and the change is logged with the user.
- Given PagerDuty fails and Slack succeeds, when the next job runs, then only PagerDuty receives the items again.

**US-5 — Keep secrets and the network safe** (FR-15, NFR-2)
*As an operator, I want keys and internal addresses protected, so that the app cannot be used to reach inside our network.*
- Given a saved key, then the API shows only whether it is set and its last four characters.
- Given a Prometheus URL whose host resolves to a private, loopback or metadata address, then it is refused unless `PROM_ALLOW_PRIVATE=1` (metadata always).
- Given a request forwarded by a proxy and no password, then it gets 403.

**US-6 — Test it on my own data first** (FR-13, FR-14)
*As an evaluating team, I want to upload our metrics and past incidents and see how the tool would have done, so that we trust numbers from our own data, not GAIA's.*
- Given a metrics file and past problems, when I evaluate, then each series is tuned on its early part and scored once on the rest, with the rules we already run and a chance line.
- Given I click *Use these settings*, then the live queue scores new data the same way the report did.

**US-7 — Teach it** (FR-8, FR-10)
*As an on-call engineer, I want to mark items Real or Noise, so that the alert model learns our environment.*
- Given marks on shown items, when the next batch is scored, then the marks become labels and a retrain reminder appears after 7 days or new Real marks.
- Given no labels at all, then the queue runs on rules only and says so.

**US-8 — Reproduce the report** (FR-16, NFR-7)
*As an examiner, I want every number in the report to come from a script and be checked, so that the text cannot drift from the code.*
- Given the result files, when `run_validate.py` runs, then it fails if any value in the report's Checked numbers table no longer matches, or if a guarded claim (for example "the detector wins 8/8 weeks") stops holding.

### Known gaps in verification

- `product/datasets.py` (NAB download) is excluded from coverage because it needs the network.
- NFR-5's "under an hour" and NFR-11's load test are measured by hand, not in CI.
- R1 through R8 in `docs/threat_model.md` are closed and tested.
- FR-21's cuML-versus-sklearn tolerance and the XGBoost CUDA conversion check are skipped on machines without a CUDA device, including CI. The CPU fallback and the skops round-trip are not skipped.
